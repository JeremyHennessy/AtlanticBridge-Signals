Baseline cd1cbc5c3d1894e5d06075e73422e8b5fe1ae20b. Diagnostic 35850570160 captured an active company-monitor workflow on default branch main, an unarchived/enabled repository created September 18, and zero schedule-triggered executions. The source health still represented September 22. Diagnostic artifact 10745371595 SHA256 6ae2da4231c4fa0325fb824f0346cf4c08b7394f4e5dc0a1c91d1f6c6301fd53 retains these reads. Its optional baseline-source export failed and is empty; it is not used as a source archive. The independently downloaded accepted PR112 source reconstructs exact baseline tree 2332207be10987a02e0daf4e44cd2ae050901f2e.

This establishes an absent scheduler invocation, not a failing collector. GitHub documents delayed/dropped scheduled events (https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows#schedule), but that does not prove the cause of this particular absence. No schedule actor or provider-side failure is invented.

The isolated recovery controller dispatched only the existing active monitor on unchanged main after checking no current-day/active attempt existed. Canonical run 35850712409 succeeded on September 23. Health reports 381 retained observations, 11 review-only changes, zero public alerts, two successful UTC dates. This is a manual catch-up, not a successful cron test or a fourteen-day reliability result.

The delivery guard adds a separate 11:47 UTC check and a check after the canonical Pages workflow. It preserves the 09:37 UTC primary schedule and a 30-minute grace period. It dispatches the same monitor only when the date is absent from both health and run inventory. Active/queued/failed/stalled runs, disabled workflows, missing state after a completed attempt, corrupt/future clocks, changed main and incomplete run inventory are never silently reset or retried. Fifteen isolated tests cover these boundaries. The guard writes no source state or main content, and never counts a dispatch as collection success.

Limits: a provider-wide scheduler outage can affect both cron events. Post-deployment checks and the separate existing reliability notification watch provide additional detection, not an uptime guarantee. Only future retained canonical collections establish reliability. This increment changes no collector, scoring gate, observation clock, UI or saved work.
