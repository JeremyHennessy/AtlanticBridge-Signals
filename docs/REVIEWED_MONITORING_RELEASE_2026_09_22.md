## Operational monitoring

The accepted company-source Ledger remains the only change detector. A portable,
checksummed checkpoint preserves its record IDs, fingerprints, source contracts,
and first/last observation clocks across independent processes and GitHub runs.
The dedicated `monitoring-state` branch contains only monitoring metadata, health,
bootstrap authorization and run histories. It does not contain source bodies,
job descriptions, contact details, user notes, executable workflows or public
lead approvals. Full source responses remain in Actions evidence artifacts.

The first import is explicitly pinned to the accepted eight-source proof artifact
10717489758 and SHA-256
`003c42f02705066074a87bc5cac33ac0c72833d1c4a03bed3b01a1c5b660874a`.
The seed preserves 373 original observations. After initialization, a missing or
corrupt checkpoint fails instead of starting a new baseline. Source contract
changes require an explicit migration; no global reset is automatic.

The daily workflow is scheduled at 09:37 UTC, separate from Pages deployments.
A source failure preserves last-good records and its last-success timestamp,
records an explicit failure with unknown counts, attempts the other sources,
commits the health report, and fails the workflow. Corrupt state or raw hashes
prevent promotion. Pushes are fast-forward only and protected from concurrent
monitor writers by a workflow concurrency group. Main is never changed by the
monitor. The initial push/PR proof exercises two separate monitor processes;
scheduled production runs do not depend on the expiring seed artifact after
successful initialization.

The in-app “Load monitoring status” control reads that branch on demand. It
checks last-attempt freshness against the reader's current time. An unavailable
health endpoint never becomes a zero-record or healthy result. Successful UTC
days are counted separately from run count; repeated runs cannot satisfy the
14-day operational target. A latest failed run cannot report that target met.
There is no claim that scheduled jobs are guaranteed to run at an exact minute.

## Retention boundary — intentionally unresolved

Metadata, source dates, fingerprints and reviewed summaries survive artifact
expiry through Git history. Raw responses in this public repository's Actions
artifacts retain the existing 90-day expiry. This is **not** a twelve-month raw
archive and does not qualify as contemporaneous historical backtest evidence.
Longer raw retention needs an approved archive/access arrangement. No source-rights
approval or private-storage deployment is invented. The schedule is real when
merged, but fourteen days of reliability and customer usefulness still require
elapsed observation and actual independent reviewers.

## Acceptance and rollback

Require full Python/Node tests, the existing source proofs, the new two-process
monitor proof, desktop/tablet/iPhone/narrow-phone browser acceptance, and exact
hosted assets before acceptance. Verify actual downloads, reload persistence,
source provenance, reviewed-source failure, degraded monitor health and escaped
notes. Local navigation restrictions are not a substitute for hosted testing.

Rollback is the isolated application commit, preserving the data branch and its
checksummed history. The monitor workflow can be disabled without removing
accepted data. Neither rollback nor a retry may overwrite user notes, reset first
observations or alter any historical backtest denominator.
